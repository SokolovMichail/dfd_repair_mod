# Как устроен мод HEMTT Spares (HEMTT Spares + HEMTT Repair)

Документ для того, кто будет мод поддерживать или делать следующий по образцу. Сводка фактов о движке
(адреса, поля, слоты) — в [`engine_notes.md`](engine_notes.md); здесь — как из них сложен мод и почему так.

## 1. Задача и общая схема

Мод добавляет две машины снабжения. Обе работают в режиме F4 так же, как HEMTT Supply раздаёт боеприпасы,
только делают другое:

- **HEMTT Spares** (`Fnd_HEMTT_repair`) — раздаёт всем машинам в зоне **запчасти**;
- **HEMTT Repair** (`Fnd_HEMTT_repairer`, пока тестовая) — **чинит** модули своим и союзным машинам в зоне и
  **восстанавливает им броню**.

Запчасти в движке почти готовы: компонент `SparesRechargerFacet` (способность `support`) уже умеет искать машины
в радиусе и пополнять им запчасти, но до режима F4 его не довели. Ремонт (`RepairerFacet`, способность `repair`)
недоделан всерьёз — см. 5.6. Броню в бою не восстанавливает вообще ничто. Одними данными этого не исправить,
поэтому мод состоит из двух частей:

```
┌──────────────────────────── данные (mods/HEMTT_Spares) ─────────────────────────────┐
│ Fnd_HEMTT_repair:   abilities = ammunition_recharge,support   (HEMTT Spares)          │
│ Fnd_HEMTT_repairer: abilities = ammunition_recharge,repair    (HEMTT Repair)          │
│ магазин кампании, армия скирмиша, локализация, значки, материалы кругов зоны          │
└──────────────────────────────────────────────────────────────────────────────────────┘
                      │ игра монтирует как обычный мод (меню MODS)
                      ▼
┌──────────── bin\winhttp.dll (загрузчик) ────────────┐      ┌──── bin\plugins\SparesSupply.dll ────┐
│ подменяет системную winhttp.dll, пересылает её 92   │ ───► │ ждёт logic.dll, находит в ней нужные │
│ функции и загружает все bin\plugins\*.dll           │      │ места и правит их в памяти            │
└─────────────────────────────────────────────────────┘      └───────────────────────────────────────┘
```

Файлы игры на диске не меняются; всё, что делает плагин, существует только в памяти запущенной игры.

## 2. Данные

Собираются скриптом [`mod/build_mod.py`](../mod/build_mod.py) из **текущих** файлов установленной игры.

**Откуда берутся файлы.** Игра монтирует слои: `basis.pak → patch_NNN*.pak → распакованная папка basis/`, и каждый
следующий файл заменяет предыдущий целиком. [`mod/tools/gamefiles.py`](../mod/tools/gamefiles.py) для каждого
нужного файла находит последний источник, где он есть, и достаёт его (архивы — zip с паролем `DFD_PAK_PASSWORD`).
Поэтому в проекте нет копий файлов игры, а после обновления игры достаточно пересобрать мод.

**Что меняется.** Мод тоже заменяет файлы целиком, так что в него кладётся полный файл игры с правками.
Правки делает [`patch_table.py`](../mod/tools/patch_table.py): он работает с Excel-XML как с текстом и меняет
только нужные ячейки, остальной файл сохраняется байт-в-байт.

Обе машины описаны в списке `UNITS` в начале `build_mod.py` (имя, описание, колонки таблицы, значок, магазин);
каждая таблица правится по очереди для всех машин из списка. Новую машину по тому же образцу добавляют туда же.

| Файл мода | Что в нём |
|---|---|
| `basis/scripts/species/cars.xml`, `dlc/Resistance/.../cars.xml` | строки `Fnd_HEMTT_repair` и `Fnd_HEMTT_repairer` — копии `Fnd_HEMTT_ammunition` (её 3D-модель, ходовые качества). Spares: `abilities=ammunition_recharge,support`, `spares=10000`. Repair: `abilities=ammunition_recharge,repair`. Обе: `capacity_ammo_recharger=500`, `unit_set=light_vehicle` (пока тест), свои `tech_pic`/`garrison_pic`. Два файла, потому что скирмиш монтирует только основной слой, а кампания Resistance — ещё и слой DLC. |
| `basis/scripts/default_army.toml` | обе машины в списке Founders (скирмиш) |
| `dlc/Resistance/.../shop_presets.xml` | Spares: 1 шт. в `sector_1_reward` + в наградах, где выдаётся HEMTT Supply. Repair: 1 шт. в `sector_1_reward` |
| `dlc/Resistance/.../encyclopedia_dlc.xml` | статьи с собственными картинками |
| `localization/en/...`, `dlc/Resistance/localization/en/...` | имена «HEMTT Spares» / «HEMTT Repair» и тексты статей |
| `basis/textures/ui/pictures/tech_pic/...fnd_hemmit_spares*.dds` | значки Spares: силуэт HEMTT с ящиком инструментов вместо снарядов ([`make_unit_icons.py`](../mod/art/make_unit_icons.py) `--kind spares`) |
| `basis/textures/ui/pictures/tech_pic/...fnd_hemmit_repair*.dds` | значки Repair: кран-стрела с крюком (`make_unit_icons.py --kind repair`) |
| `basis/materials/rounds/sparesRecharge.material` + `textures/cursor_decals/circle_spares.dds` | круг зоны Spares — гаечные ключи. В оригинале этот материал ссылался на безликий `circle_generic.dds` ([`make_circle_spares.py`](../mod/art/make_circle_spares.py)) |
| `basis/materials/rounds/repairRecharge.material` + `textures/cursor_decals/circle_repair.dds` | круг зоны Repair — скрещённые ключ и молоток ([`make_circle_repair.py`](../mod/art/make_circle_repair.py)). Материал новый, в игре его нет: путь к нему подставляет плагин (5.6) |
| `mod.json`, `basis/mod_icon.dds` | описание и иконка в меню MODS ([`make_mod_icon.py`](../mod/art/make_mod_icon.py)) |

**Почему `ammunition_recharge,support` / `ammunition_recharge,repair`.** Кнопку F4 игра даёт только машинам с
боеприпасами или заправщиком, а сам режим F4 работает только с ними. Поэтому обеим машинам нужен компонент
боеприпасов как «носитель» режима, а раздавать патроны им запрещает плагин. Запас 500 патронов — просто данные,
никуда не уходят. Заправщик (`refuel`) не подходит: он раздаёт топливо из бака самой машины. У HEMTT Repair
компонент ремонта `RepairerFacet` служит только меткой «это ремонтная машина» — сам ремонт делает плагин.

## 3. Загрузчик `bin\winhttp.dll`

Игра не умеет подключать нативные плагины, поэтому используется подмена DLL: `game.dll` (и встроенный браузер
`libcef.dll`) импортируют `winhttp.dll`, а Windows ищет её сначала рядом с программой — в `bin\`.

[`loader/dllmain.cpp`](../loader/dllmain.cpp) при загрузке:

1. Определяет, основной ли это процесс. Вспомогательные процессы встроенного браузера (CEF, в командной строке
   есть `--type=`) тоже грузят эту DLL — в них она только пересылает вызовы, без плагинов и без лога.
2. Загружает настоящую `%SystemRoot%\System32\winhttp.dll` и запоминает адреса всех её 92 функций в `g_orig[]`.
3. Загружает все `bin\plugins\*.dll` по алфавиту и пишет `bin\plugins\loader.log`.

Пересылка устроена через переходники на ассемблере ([`loader/winhttp_exports.S`](../loader/winhttp_exports.S)):
каждая экспортируемая функция — одна инструкция `jmp *g_orig+8*i(%rip)`, то есть вызов уходит в системную DLL
с теми же регистрами и стеком, ничего не зная о сигнатуре функции. Переходники, `.def` с экспортами и список имён
генерирует [`tools/gen_winhttp_proxy.py`](../tools/gen_winhttp_proxy.py) из таблицы экспорта системной DLL.

Плагины грузятся прямо из `DllMain` загрузчика, то есть под loader lock Windows. Это сделано, чтобы успеть до
загрузки `logic.dll`, но накладывает правило: в `DllMain` плагина нельзя вызывать `LoadLibrary` и ждать другие
потоки — только зарегистрироваться (см. ниже).

## 4. Общий код плагинов — [`common/patch.h`](../common/patch.h)

| Что | Зачем |
|---|---|
| `Log` | файл `<имя>.log` рядом с плагином, строки со временем |
| `DllWatcher` | вызывает колбэк, как только в процесс загружена нужная DLL: сразу, если уже загружена, иначе через `LdrRegisterDllNotification`. Уведомление приходит после отображения DLL в память и связывания импорта, но **до её `DllMain` и до любого её кода** — правки встают раньше, чем игра создаст первый юнит. |
| `Image` | загруженный PE-образ: секции; `find(шаблон)` — поиск байтового шаблона с `??`; `vtableOf("Класс@Leonardo")` — адрес vtable по RTTI (имя типа `.?AV...@@` → TypeDescriptor → CompleteObjectLocator → слот перед vtable) |
| `PatchSet` | набор правок «всё или ничего»: `bytes()` — замена байтов с проверкой исходных, `vslot()` — подмена указателя в vtable с проверкой, что подменяемая функция начинается с ожидаемых байтов. `apply()` сначала проверяет **все** правки и только потом пишет; при любом несовпадении не пишет ничего. |

Почему поиск, а не зашитые адреса: другая сборка игры (Steam, патч) почти наверняка сдвинет адреса, но код
тех же функций останется прежним. Шаблоны — это байты кода вокруг нужного места, где адресные смещения
(rip-относительные и `call`) заменены на `??`; каждый шаблон должен находиться ровно один раз (шаблоны получены
скриптом [`re/mksig.py`](../re/mksig.py)). А проверка начала подменяемых функций заодно подтверждает, что
смещения полей, которые читает плагин, те же самые.

## 5. Плагин `SparesSupply.dll` — [`plugins/spares_supply/spares_supply.cpp`](../plugins/spares_supply/spares_supply.cpp)

### 5.1 Модель объектов движка, которой пользуется плагин

- **Компонент** (facet) — C++-объект с vtable; у раздатчиков общие слоты: 10 `update(dt)`, 13 `deactivate`,
  14 `activate`, 17 у боеприпасов — `canRecharge(target)`. Флаг «выключен» — байт `+0x59` у боеприпасов/заправщика,
  `+0x51` у запчастей.
- **Владелец** компонента (машина) — `[компонент+0x10]` указывает на блок счётчика ссылок, в нём `[+0x10]` — объект.
- **Компоненты машины** перебираются итератором: `машина->vfunc(+0x58)` отдаёт итератор с методами «конец?»,
  «текущий», «следующий». `findFacet(машина, vtable)` — так же, как это делает сам движок, но сравнивая
  vtable компонента с нужной (точный класс). Счётчики ссылок движок меняет без блокировок — логика игры
  однопоточная, плагин работает в том же потоке.
- Перехват метода = подмена указателя в vtable класса (в `.rdata`). Это меняет поведение **всех** объектов класса,
  поэтому каждый перехват первым делом решает, касается ли его этот объект (`kindOf`: есть ли у машины компонент
  запчастей или ремонта), и иначе просто вызывает оригинал. Нужные методы вызываются только через vtable — это проверено по всему коду
  `logic.dll`, прямых вызовов нет, так что подмены указателя достаточно.

### 5.2 Что именно плагин меняет

| # | Где | Правка | Зачем |
|---|---|---|---|
| 1 | сборщики описаний машин и танков | `mov r15b,1` после найденного `support` и после найденного `repair` → `nop` (4 места) | движок не создаёт `ammunition_recharge`, если у машины уже есть `refuel`/`support`/`repair`. Без этого у наших машин нет компонента боеприпасов → нет кнопки F4 |
| 2 | `AmmoRechargerFacet` / `RefuellerFacet` слоты 14 / 13 | `activate` / `deactivate` → вызвать оригинал + включить/выключить запчасти той же машины | режим F4 включает только первый «заправочный» компонент машины; запчасти — другой интерфейс и сами в режим не попадают |
| 3 | те же классы, слот 10 `update` | оригинал + `update` запчастей с тем же `dt`, пока компонент включён | **апдейт запчастей движок сам не вызывает** — его тикает только приказ «пополнить по клику». Включённые, но не тикаемые запчасти ничего не делают |
| 4 | `SparesRechargerFacet` слот 13 `deactivate` | не выключать, пока у машины активны боеприпасы/заправщик | приказ по клику по окончании выключает запчасти — это оборвало бы раздачу в режиме F4 |
| 5 | `AmmoRechargerFacet` слот 17 `canRecharge` | «нельзя», если у машины есть запчасти или ремонт | машины мода не раздают патроны: этот метод спрашивают и раздача по зоне, и приказ по клику |
| 6 | поиск целей запчастей | радиус: константа 20 м → глобальный `supplyRadius` (`movss` с другим адресом) | зона запчастей совпадает с нарисованным кругом. Сейчас `supplyRadius` тоже 20, правка на случай, если игра его поменяет. Константу 20.0 саму не трогаем: её читает и другой код |
| 7 | рисование круга `AmmoRechargerFacet` | перерисовать круг материалом `sparesRecharge` / `repairRecharge` | см. 5.3 и 5.6 |
| 8 | `AmmoRechargerFacet::update` (тот же перехват 3) | у HEMTT Repair: импульс ремонта раз в 0,5 с | ремонт модулей и брони машинам в зоне — см. 5.6 |
| 9 | `RepairerFacet` слоты 14 / 13 / 10 | `activate` / `deactivate` → оригинал + то же для боеприпасов; `update` → ничего | режим F4 у HEMTT Repair управляет компонентом ремонта, а не боеприпасами — см. 5.6 |

### 5.3 Жизненный цикл режима F4 с плагином

```
игрок жмёт F4
  └─ AiUnpack/AiDoRechargeState → AmmoRechargerFacet::activate        (перехват 2)
        ├─ оригинал: включить боеприпасы, нарисовать круг (ammoRecharge)
        ├─ syncSpares(on): найти у машины запчасти → SparesRechargerFacet::activate
        └─ convertCircle: перерисовать круг материалом sparesRecharge     (правка 7)
каждый кадр
  └─ движок → AmmoRechargerFacet::update                                (перехват 3)
        ├─ оригинал: canRecharge(цель) = false → патроны никому          (перехват 5)
        └─ компонент включён → SparesRechargerFacet::update(dt):
              раз в 1/скорость с → найти машины в радиусе supplyRadius   (правка 6)
              → пополнить запчасти, списать со своего запаса
игрок сворачивает режим
  └─ AmmoRechargerFacet::deactivate → оригинал (убрать круг) → запчасти off
```

**Круг (правка 7).** Круг зоны рисует функция компонента боеприпасов: она берёт материал из таблицы материалов
по смещению, зашитому в инструкцию `lea r8,[rax+0x120]` (`0x120` — ammoRecharge, `0xE0` — sparesRecharge).
Плагин держит эту инструкцию записываемой и при перерисовке на время одного вызова функции подставляет `0xE0`,
затем возвращает `0x120` — остальные машины по-прежнему рисуют свои круги. Перерисованные круги запоминаются
(`g_ownCircles`), чтобы не перерисовывать их каждый кадр. Перерисовка вызывается и из `activate`, и из
`update` — второе нужно для круга, созданного без участия плагина (при загрузке сохранения).

### 5.4 Установка правок

`DllMain` плагина только открывает лог и регистрирует `DllWatcher` на `logic.dll`. Когда она загружается:

1. `resolve()` — поиск всех адресов:
   - пять vtable по RTTI: боеприпасы, заправщик, запчасти, ремонт, модули (`DamageableModulesFacet`);
   - места кода по шаблонам, каждый ровно 1 раз; «support блокирует ammo» — ровно 2;
   - «repair блокирует ammo» — общий шаблон `mov r15b,1; …; lea rcx,[имя компонента]` встречается 5 раз, нужные
     2 выбираются по строке `[Leonardo.RepairerFacet]`, на которую указывает `lea` (`Image::findString`);
   - адреса функций, которые плагин вызывает сам, — из `call` внутри уже найденного кода: `incHealth` (из
     `RepairerFacet::update`), «дипломатия мира» (из `canRecharge`, его начало проверено), «таблица материалов»
     (за 12 байт до `lea` материала круга);
   - адрес `supplyRadius` — из rip-относительной инструкции, которая его читает.
2. `PatchSet`: 4 замены байтов, радиус, 12 подмен слотов vtable (каждая с проверкой начала функции),
   проверка инструкции круга. `apply()` — всё или ничего.
3. Страница с инструкцией круга делается записываемой (для правки 7), в лог — `SparesSupply active`.

Если что-то не нашлось или не совпало, в лог пишется, что именно, и игра работает без изменений. Данные мода
при этом всё равно подключены: HEMTT Spares есть и пополняет запчасти по клику, только без кнопки F4;
HEMTT Repair ездит, но ничего не чинит.

### 5.5 Диагностика

`bin\plugins\SparesSupply.log`: версия, адрес `logic.dll`, найденные vtable и функции, список поставленных
правок с RVA. Во время игры — первые 50 событий (включение/выключение запчастей и ремонта, перерисовка круга),
первые 20 секунд работы зоны запчастей (`radius`, `targets` — сколько машин компонент нашёл в зоне) и первые
40 импульсов ремонта (`repair: target=… +N hp, M armor layers, total hp …`).

### 5.6 HEMTT Repair: ремонт и броня

**Почему не движковый ремонт.** Компонент `RepairerFacet` (способность `repair`) в движке недоделан:

- создаётся выключенным, и включает его никто;
- его `update` (`0x363790`) ищет машины в радиусе, но результат поиска тут же выбрасывает — список целей, по
  которому он потом чинит, всегда пуст;
- команду цели он не проверяет вообще (фильтр поиска отсекает только саму машину) — чинил бы и врагов;
- чинит один модуль за импульс и броню не трогает.

Поэтому ремонт делает плагин, а `RepairerFacet` служит меткой. Но выбросить его совсем нельзя: `IRepairerFacet`
наследует `IRechargerFacet`, и компонент ремонта создаётся раньше боеприпасов — режим F4 берёт первый
раздатчик машины и включает/выключает **его**. Поэтому плагин перехватывает слоты 14/13 `RepairerFacet`: флаги
ставятся как обычно (режим F4 спрашивает «включён ли»), а включение дублируется на компонент боеприпасов.
Собственный `update` ремонта (слот 10) заглушён.
Цели он берёт у компонента боеприпасов: тот в своём `update` уже собирает машины в радиусе `supplyRadius`
(список `[ammo+0x30]`, тем же поиском, что и у ремонта) — и рисует ровно этот круг.

**Импульс ремонта** (`tickRepair`, раз в `kRepairPeriod` = 0,5 с, пока включён режим F4). Для каждой машины
из списка:

1. Пропускает саму HEMTT Repair и чужих. «Свой» — как в `AmmoRechargerFacet::canRecharge`: дипломатия мира
   (`0x541a00`) сравнивает команды цели и владельца; отношение 2 или 4 — нельзя. Цель без команды — тоже нельзя.
   То есть HEMTT Repair чинит тех же, кому HEMTT Supply дал бы патроны.
2. Находит у машины `DamageableModulesFacet` (у пехоты его нет — пропуск). Машина с общим здоровьем 0
   (уничтоженная) пропускается.
3. **Модули:** каждому повреждённому — `+max(1, 2% максимума)` через `DamageableModulesFacet::incHealth`
   (`0x225ba0`). Это тот же путь, что у ремонта экипажем: движок сам пересчитывает общее здоровье, состояние
   модуля («повреждён» / «уничтожен»), визуал и синхронизацию. От нуля до полного — около 25 с.
4. **Броня:** каждому слою на каждой из 6 сторон каждого модуля — `+2%` исходной толщины, но не больше исходной.
   Текущая толщина — `vector<float>` в состоянии модуля, исходная — в описании модуля (раскладка — в
   `engine_notes.md`). Функция урона читает текущую толщину напрямую, так что восстановленная броня сразу снова
   работает. Своей функции «восстановить броню» в движке нет — значения пишутся напрямую.

Скорости — константы `kRepairPeriod`, `kRepairFraction`, `kArmorFraction` в начале плагина.
**Цена — запчасти самой HEMTT Repair** (у неё 10000; её может пополнять HEMTT Spares). Модуль — 1 запчасть
за 1 восстановленного здоровья, броня — `kSparesPerMm` (1) запчасть за 1 мм толщины; дробная цена брони копится
и списывается целыми запчастями. `incHealth` — это ремонт экипажем, он сам списывает запчасти у **цели**
(`[модули+0x130]` минус прибавка здоровья); плагин запоминает запас цели до вызова и возвращает после — цель
не платит. Прибавка модулю ограничена остатком склада; склад пуст — импульс ничего не делает
(`repair: out of spare parts` в логе).

**Круг зоны.** Материал берётся из таблицы, где у нас нет своей строки, а смещение в `lea` (как у запчастей)
не может указать за пределы таблицы. Поэтому на время одного вызова функции круга плагин подменяет саму строку
`ammoRecharge` в таблице (`std::string` MSVC: указатель, длина, ёмкость) на путь
`materials/rounds/repairRecharge.material` и сразу возвращает её обратно. Таблица перед этим инициализируется
вызовом её же функции; строка с путём — статическая в плагине, так что живёт всё время игры.

## 6. Сборка и релиз

```
cmake --build <build> --target release
  ├─ вложенная Release-сборка: winhttp.dll, SparesSupply.dll (-O3, -s, статически, UCRT)
  ├─ mod/build_mod.py   → <build>/release/stage/mods/HEMTT_Spares
  └─ mod/package.py     → dist/HEMTT_Spares_v<MOD_VERSION>.zip  (+ _cover.png)
```

DLL линкуются полностью статически, с системным UCRT, — нужны только `KERNEL32.dll` и `api-ms-win-crt-*`, которые
есть в любой Windows 10/11 (у MinGW из комплекта CLion статическая `libwinpthread` собрана под UCRT, поэтому
`-mcrtdll=ucrt` обязателен). Цели и подготовка окружения — в основном [`README.md`](../README.md).

## 7. Ограничения

- Только одиночная игра: правки меняют логику игры, в мультиплеере будет рассинхрон.
- HEMTT Repair — тестовая: лёгкая техника, скорости ремонта не выверены, проверена только офлайн.
- Конфликт с модами, заменяющими те же файлы (список — в [`INSTALL.md`](../INSTALL.md)), и с другими
  программами, использующими `bin\winhttp.dll`.
- Если игра обновится и код поменяется — плагин откажется работать (см. лог); нужно обновить шаблоны:
  найти новое место в `re/` и получить шаблон через `re/mksig.py`.
